# Доработка linked-list: пошаговые задания

Задания идут строго по порядку — каждое следующее опирается на предыдущее. Код пишется
самостоятельно; здесь только условия, шаги и критерии приёмки.

**Общее правило для всех заданий.** Работа считается сданной, когда выполнены все три проверки:

```sh
gcc -std=c17 -Wall -Wextra -Wpedantic -c list.c -o /dev/null   # ноль предупреждений
make build && ./main                                            # ASan/UBSan молчат
valgrind --leak-check=full --show-leak-kinds=all ./main          # 0 errors, 0 bytes lost
```

Для valgrind нужна сборка **без** санитайзеров — они конфликтуют. Это учтено в задании 7.

## Задание 1. Откатить `int *value` — это тупик

### Условие

Сейчас в `list.h` поле узла объявлено как `int* value`, а «пустой список» изображается одним
узлом со значением `NULL`. Идея понятна: раз `append` не умеет работать с пустым списком, вы
сделали так, чтобы пустых списков не существовало — вместо них узел-пустышка.

Проблема в том, что цена этого решения выше, чем польза:

1. `append` кладёт в поле-указатель целое число через `(int *) value`. Компилятор предупреждает:
   `cast to pointer from integer of different size`. На 64-битной платформе `int` — 32 бита,
   указатель — 64. Число превращается в адрес, по которому ничего нет. Разыменовать такой
   указатель нельзя, а значит и значение обратно не достать.
2. `print_list` печатает `&head->value` по формату `%d`. Это адрес поля структуры, а не
   значение; типы не совпадают (`int **` против `int`), компилятор предупреждает и об этом.
   Числа, которые вы видите на экране, — мусор.
3. Узел-пустышка (sentinel) ломает все остальные операции: `length` должна считать его или нет?
   `free_list` освобождает и его тоже? Как отличить «список пуст» от «список из одного
   элемента, равного нулю»? Каждая новая функция потребует отдельной ветки для этого случая.

Правильное представление пустого списка в C — **указатель на голову равен `NULL`**. Никакого
особого узла не нужно. А то, что `append` не может превратить `NULL` в первый узел, решается не
пустышкой, а передачей **адреса** указателя — это задание 3.

### Что сделать

1. Вернуть в `list.h` поле `int value` (значение, не указатель).
2. Вернуть `create_node(int value)` и `append(Node *head, int value)` — без приведений типов.
3. В `print_list` печатать `head->value`, а не `&head->value`.
4. `init_list` пока оставить как есть — он исчезнет в задании 3.

### Готово, когда

`gcc -std=c17 -Wall -Wextra -Wpedantic -c list.c -o /dev/null` не печатает ничего, и
`./main` выводит те числа, которые вы клали в список.

## Задание 2. Обработка неудачи `malloc` без `exit`

### Условие

Сейчас `create_node` при неудачном `malloc` печатает сообщение и вызывает `exit(1)`.

Так делать нельзя по трём причинам:

- **Библиотека не принимает решение за программу.** `list.c` — это переиспользуемый модуль.
  Завершать чужой процесс — не его полномочие: вызывающий мог бы освободить ресурсы, сохранить
  данные, попробовать ещё раз или продолжить работу без этого узла. `exit()` отбирает у него
  выбор. Решение о завершении принимает `main`.
- **Диагностика идёт не туда.** Сообщения об ошибках печатаются в `stderr`, а не в `stdout`:
  `stdout` может быть перенаправлен в файл или в конвейер, и ошибка там потеряется. `stderr` к
  тому же не буферизуется, поэтому сообщение не пропадёт при аварийном завершении.
- **Нет перевода строки.** Строка без `\n` слипается со следующим выводом.

### Что сделать

1. Убрать `exit()` из `create_node`. При неудаче `malloc` функция возвращает `NULL` — это и есть
   признак ошибки для вызывающего.
2. Диагностику либо убрать совсем (пусть решает вызывающий), либо писать в `stderr` через
   `fprintf` и с `\n` на конце. Выбрать один вариант и записать выбор в README.
3. Все места, где вызывается `create_node`, должны проверять результат на `NULL` и как-то
   реагировать — как именно, решаете вы, но молча игнорировать нельзя.
4. Заодно убрать приведение `(Node *)` у результата `malloc` — в C оно не нужно и умеет прятать
   ошибки. И убрать бессмысленную инициализацию `Node* head = NULL;` перед немедленным
   присваиванием; заодно переименовать переменную — это один узел, а не голова списка.

### Как проверить

Ограничить виртуальную память процесса через `ulimit -v` и посмотреть на единственный вызов
`create_node` из `main` — способ ненадёжный: между лимитом, при котором ещё не грузится сам
динамический загрузчик (`error while loading shared libraries`), и лимитом, при котором хватает
памяти на пару узлов списка, почти нет зазора — конкретное число сильно зависит от машины и от
того, собран ли бинарник с санитайзерами (у ASan рантайм резервирует память сам по себе).

Надёжнее — вызывать `create_node` в цикле, пока не вернётся `NULL`, тогда лимит подбирать не
нужно, отказ гарантированно наступит:

```c
#include <stdio.h>
#include "list.h"

int main(void){
    long count = 0;
    Node *n;
    while ((n = create_node(count)) != NULL) count++;
    printf("malloc failed after %ld allocations\n", count);
    return 0;
}
```

```sh
gcc -std=c17 -Wall -Wextra -Wpedantic list.c malloc_fail_test.c -o /tmp/malloc_fail_test
bash -c 'ulimit -v 3000; /tmp/malloc_fail_test'
```

Это отдельный временный тестовый файл, не часть проекта — после проверки можно удалить.

### Готово, когда

Ни одна функция в `list.c` не вызывает `exit()`, а неудача выделения памяти доходит до `main`
как возвращаемое значение.

## Задание 3. Пустой список и владение памятью

Это ключевое задание проекта. Здесь решаются сразу две проблемы, и обе — про одну и ту же
особенность языка.

### Условие

В C аргументы передаются **по значению**, включая указатели. Функция получает копию указателя.
Изменить саму копию можно, но у вызывающего переменная останется прежней. Отсюда два симптома:

**Симптом первый — нельзя создать список из ничего.** `append(Node *head, ...)` получает копию
`head`. Если список пуст (`head == NULL`), функция может выделить узел, но записать его адрес в
переменную вызывающего не может — она видит только копию. Именно поэтому появился `init_list`,
навязывающий обязательный первый элемент, а потом и узел-пустышка из задания 1.

**Симптом второй — висячий указатель после освобождения.** Тело `free_list` написано верно:
`next` сохраняется до `free(head)`, обход не падает, память освобождается вся. Но обнулить
`head` у вызывающего функция не может. В `main.c` проверка `if (head == NULL)` после
`free_list(head)` **всегда ложна** — вы это уже видели, поэтому и закомментировали следующий
`print_list`. Если его раскомментировать, получится чтение освобождённой памяти.

Обе проблемы решаются одинаково: функция должна получать не указатель на голову, а **адрес
переменной**, в которой этот указатель лежит, — то есть `Node **`. Тогда через `*head` она
меняет саму переменную вызывающего.

### Что сделать

1. Договориться о представлении: **пустой список — это `head == NULL`**. Никаких узлов-пустышек.
   `init_list` в текущем виде удаляется; список заводится обычным `Node *head = NULL;`.
2. Перевести на `Node **` все операции, которые могут изменить голову: добавление в начало,
   вставку по индексу, удаление по индексу, удаление с конца, освобождение списка. Операции,
   которые голову не меняют (печать, поиск, длина), оставить с `Node *`.
3. `free_list` после освобождения выставляет `*head = NULL`.
4. В `main` убедиться, что после `free_list(&head)` проверка `head == NULL` истинна, и
   раскомментировать `print_list` — теперь он корректно напечатает пустую строку.

### Альтернатива, которую надо рассмотреть и отклонить (или принять)

Второй способ — не менять сигнатуру, а зафиксировать в контракте: «после `free_list` указатель
невалиден, обнуляет его вызывающий». Так устроен `free()` из stdlib. Это работает, но забыть
обнуление легко, и компилятор не напомнит.

Выбрать один из двух подходов и **записать в README, почему**. Это часть задания.

### Граничные случаи

- пустой список (`*head == NULL`) — все операции должны его переживать;
- список из одного элемента;
- двойной вызов `free_list` — при варианте с `Node **` он безвреден, объясните в README почему.

### Как проверить

Собрать с `-fsanitize=address` (уже в makefile) и убедиться, что `heap-use-after-free` не
возникает.

### Готово, когда

`main` заводит список как `Node *head = NULL;`, наполняет его, освобождает — и после
освобождения `head == NULL` истинно, а обращение к списку безопасно.

## Задание 4. Полный набор операций

### Условие

Сейчас список умеет только добавлять в конец и удалять с конца. Для учебной структуры данных
этого мало — и большинство ошибок с указателями живут именно в операциях вставки и удаления в
середине.

### Что сделать

Реализовать, соблюдая правило из задания 3 (меняет голову → принимает `Node **`):

| Операция | Что делает | Сложность |
|---|---|---|
| `push_front` | вставка в начало | O(1) |
| `push_back` | вставка в конец | O(n) |
| `insert_at` | вставка по индексу | O(n) |
| `remove_at` | удаление по индексу | O(n) |
| `pop_back` | снять последний, вернуть значение | O(n) |
| `find` | найти первое вхождение, вернуть индекс или признак «не найдено» | O(n) |
| `length` | число элементов | O(n) |
| `reverse` | развернуть список на месте, без выделения новых узлов | O(n) |

Отдельное требование к `pop_back` (и `remove_at`): функция должна и вернуть снятое значение, и
сообщить об ошибке, если список пуст. Одним `int` это не выражается — любое значение может быть
легальным элементом списка. Два стандартных решения:

- вернуть код успеха (например, `bool`), а значение отдать через out-параметр `int *out`;
- вернуть значение, а признак ошибки отдать через out-параметр.

Выбрать один и применить единообразно ко всем операциям, которые могут не сработать. Обосновать
в README.

Отдельное требование к `reverse`: разворот делается перестановкой указателей `next` у
существующих узлов. Если внутри появился `malloc` — задание не выполнено.

### Граничные случаи (проверить каждый)

- пустой список: `length` = 0, `find` не находит, `pop_back` сообщает об ошибке, `reverse` не
  падает, `print_list` печатает пустую строку;
- список из одного элемента: `pop_back` должен опустошить его и выставить голову в `NULL`
  (сейчас `pop` на таком списке падает — `head->next->next` при `head->next == NULL`);
- `insert_at` с индексом `0` — вставка в начало, голова меняется;
- `insert_at` с индексом, равным `length`, — вставка в конец, допустима;
- `insert_at` с индексом больше `length` — ошибка, список не меняется;
- `remove_at` с индексом `0` и с индексом `length - 1`;
- `remove_at` с индексом `length` и больше — ошибка, список не меняется;
- отрицательный индекс — решите, какой тип использовать для индекса, и обоснуйте в README:
  беззнаковый `size_t` делает отрицательный индекс невозможным по построению, но `-1` при
  передаче молча превратится в огромное число.

### Готово, когда

Все операции из таблицы реализованы, каждый граничный случай из списка выше отрабатывает
предсказуемо, санитайзеры и valgrind чисты.

## Задание 5. Тесты

### Условие

Сейчас корректность проверяется глазами по выводу `print_list`. Это не масштабируется: в задании
4 появилось восемь операций и два десятка граничных случаев, глазами их не удержать.

### Что сделать

1. Завести отдельный файл с тестами (например, `test.c`) со своей функцией `main`. В сборке
   участвуют `list.c` + `test.c`; исходный `main.c` остаётся отдельной демонстрационной
   программой.
2. Использовать `assert` из `<assert.h>`. Каждый граничный случай из задания 4 — отдельная
   проверка.
3. Каждый тест обязан освобождать свой список — иначе valgrind на тестах покажет утечки.
4. Проверять не только возвращаемые значения, но и состояние списка после операции: длину и
   последовательность элементов.

### Критерий приёмки (обязательно выполнить)

Тесты бесполезны, пока не доказано, что они умеют падать. Проверьте это руками:

1. Внесите в `list.c` намеренную ошибку — например, замените `<` на `<=` в проверке границ
   индекса, или уберите обновление `next` в одной из вставок.
2. Запустите тесты. Они **должны** упасть с указанием конкретного `assert`.
3. Верните код обратно, убедитесь, что тесты снова проходят.

Если тесты прошли с внесённой ошибкой — они ничего не проверяют, вернитесь к пункту 2.

### Готово, когда

`make test` собирает и прогоняет тесты, все проходят, valgrind на тестах чист, и проверка на
намеренную ошибку выполнена.

## Задание 6. Makefile

### Условие

Текущий makefile собирает всё одной командой и имеет три недостатка:

- **нет зависимости от `list.h`** — правка заголовка не вызывает пересборку, и вы получите
  несогласованные объектные файлы;
- **цели не объявлены `.PHONY`** — если в каталоге появится файл с именем `build`, `clean` или
  `run`, make решит, что цель уже собрана, и ничего не сделает;
- **санитайзеры зашиты в единственную цель сборки** — а valgrind с ними конфликтует, для него
  нужна отдельная сборка;
- цель `all: build run clean` удаляет бинарник сразу после запуска, что мешает отлаживать.

### Что сделать

Собрать makefile с целями:

| Цель | Назначение |
|---|---|
| `debug` | `-g -O0 -fsanitize=address,undefined` — повседневная разработка |
| `release` | `-O2` без санитайзеров — сборка под valgrind |
| `test` | собрать и прогнать тесты из задания 5 |
| `valgrind` | собрать `release` и прогнать под valgrind с `--leak-check=full` |
| `clean` | удалить бинарники и объектные файлы |

Требования:

1. Общие флаги (`-std=c17 -Wall -Wextra -Wpedantic`) вынести в переменную и не дублировать.
2. Каждая цель, зависящая от исходников, должна зависеть и от `list.h`.
3. Все цели, не создающие одноимённого файла, перечислить в `.PHONY`.
4. Бинарники разных целей не должны затирать друг друга — иначе `make valgrind` после
   `make debug` прогонит сборку с санитайзерами.
5. Добавить `main`, `*.o` и прочие артефакты в `.gitignore` — сейчас собранный бинарник попадает
   в `git status` как неотслеживаемый файл.

### Готово, когда

`make clean && make debug && ./main` и `make clean && make valgrind` отрабатывают с нуля, и
правка `list.h` вызывает пересборку.

## Задание 7 (растяжка). Список произвольного типа

Браться после того, как задания 1–6 полностью закрыты.

### Условие

Сейчас список умеет хранить только `int`. Чтобы хранить строки или структуры, пришлось бы
копировать весь файл и менять тип — так в C не делают. Обобщённый контейнер строится на
`void *` плюс набор функций, которые вызывающий передаёт при создании списка: эти функции знают
про конкретный тип, а сам список — нет.

Заодно это возвращает вас к вопросу владения памятью, но на новом уровне: если узел хранит
`void *`, кто освобождает то, на что этот указатель смотрит?

### Что сделать

1. Заменить поле `int value` на `void *data`.
2. При создании списка принимать три функции обратного вызова: сравнение двух элементов
   (нужно для `find`), печать элемента (для `print_list`), освобождение элемента (для
   `free_list` и удаляющих операций).
3. Явно решить и записать в README: список **владеет** данными или только ссылается на них?
   От ответа зависит, вызывает ли `free_list` переданный деструктор.
4. Продемонстрировать работу на двух разных типах в одной программе:
   - список `int` — данные не требуют освобождения, деструктор пустой или отсутствует;
   - список строк (`char *`), где строки выделены через `malloc`/`strdup` и список освобождает
     их через переданный деструктор.

### Граничные случаи

- `NULL` в качестве деструктора (элементы не требуют освобождения) — не должно падать;
- `find` без переданной функции сравнения — что делать, решите и задокументируйте.

### Готово, когда

Одна программа создаёт оба списка, наполняет, печатает, ищет и освобождает — valgrind чист.
