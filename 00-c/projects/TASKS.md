Лестница заданий после первого проекта (`linked-list`). Блок A закрывает пробелы на уже
знакомом коде, блок B переносит выработанную дисциплину на новые структуры данных.

Код пишется самостоятельно — здесь только требования, граничные случаи и критерии приёмки.

## Сквозные требования

Действуют для **каждого** задания ниже. Задание не считается сделанным, пока не выполнены все
семь пунктов.

1. Сборка `gcc -std=c17 -Wall -Wextra -Wpedantic` — ноль предупреждений.
2. `valgrind --leak-check=full --show-leak-kinds=all` — `0 errors`, `definitely lost: 0 bytes`.
3. Сборка с `-fsanitize=address,undefined` — программа отрабатывает чисто.
4. Каждый заголовок: include guards; включает только то, что нужно его собственным объявлениям.
5. Каждый `malloc` / `realloc` / `calloc` проверяется на `NULL`.
6. Есть тестовый файл с проверками граничных случаев; при неверной реализации он падает.
7. В README проекта — асимптотика каждой публичной операции.

## Блок A — довести linked-list

Работа в существующем `linked-list/`.

> Развёрнутая версия этого блока — с условиями, пошаговыми инструкциями и критериями
> приёмки для каждого пункта — лежит в [`linked-list/TASK.md`](linked-list/TASK.md).
> Ниже краткая сводка.

### A1. Ошибки памяти и гигиена заголовка

**Цель:** научиться читать вывод санитайзера и доверять `-Wextra`.

**Требования:**
- корректный размер аллокации в `create_node`;
- `pop` объявлен в `list.h`;
- include guards в `list.h`;
- убраны неиспользуемые `#include`;
- убрано приведение результата `malloc`;
- `malloc` проверяется на `NULL`;
- убрана лишняя `;` после блока `while` в `print_list`;
- неудача `malloc` обрабатывается без `exit()`: библиотечная функция не завершает процесс за
  вызывающего — она возвращает признак ошибки, а решение о выходе принимает `main`. Диагностика
  пишется в `stderr` и заканчивается переводом строки.

**Проверка:** до правки зафиксировать в README вывод ASan (там heap-buffer-overflow); после
правки — оба санитайзера и valgrind чисто.

### A2. Владение памятью

**Цель:** понять, кто владеет узлами и кто их освобождает.

**Требования:**
- функция `free_list`, освобождающая весь список;
- корректна на пустом списке (`NULL`) и на списке из одного элемента;
- тело не обращается к `head->next` после `free(head)` — следующий указатель сохраняется до
  освобождения;
- `main` завершается без утечек.

**Главная ловушка.** Освободить память — половина дела; вторая половина в том, что указатель у
вызывающего после этого остаётся висячим. При сигнатуре `void free_list(Node *head)` указатель
передаётся **по значению**, поэтому функция физически не может обнулить `head` в `main` — по
той же причине, по которой `append` не умеет работать с пустым списком. Проверка
`if (head == NULL)` после такого вызова всегда ложна, а любое последующее обращение к списку —
use-after-free.

Выбрать одну из двух сигнатур и обосновать выбор в README:
- `void free_list(Node **head)` — функция сама выставляет `*head = NULL`; забыть невозможно;
- `void free_list(Node *head)` — обнуление остаётся обязанностью вызывающего, как у `free()` из
  stdlib; тогда контракт пишется в комментарии к прототипу.

**Граничные случаи:** пустой список (`NULL`); список из одного элемента; двойной вызов
`free_list`; обращение к старому указателю после освобождения.

**Критерий приёмки:** сборка с `-fsanitize=address` не даёт `heap-use-after-free`. Если выбран
вариант с `Node **` — проверка `head == NULL` сразу после вызова истинна.

### A3. API, в котором существует пустой список

**Цель:** понять, зачем нужен `Node **`, и почему передача указателя по значению не даёт
изменить голову списка.

**Требования:**
- список создаётся пустым, без обязательного первого элемента (`init_list` в текущем виде
  исчезает);
- операции: `push_front`, `push_back`, `insert_at`, `remove_at`, `pop_back`, `find`, `length`,
  `reverse`;
- `pop_back` возвращает снятое значение и **отдельно** сигнализирует об ошибке (пустой список).
  Способ выбрать самостоятельно и обосновать в README: код возврата против out-параметра.

**Граничные случаи (обязательны):**
- пустой список;
- список из одного элемента;
- `insert_at` / `remove_at`: индекс 0, индекс `length`, индекс вне диапазона, отрицательный
  индекс;
- `reverse` на пустом списке и на списке из одного элемента.

### A4. Тесты и сборка

**Цель:** перестать проверять код глазами.

**Требования:**
- файл тестов на `assert`, покрывающий все граничные случаи из A3;
- makefile с целями `debug` (`-g -O0 -fsanitize=address,undefined`), `test`, `clean`;
- объявленный `.PHONY`;
- зависимость целей от `list.h`, чтобы правка заголовка вызывала пересборку.

**Критерий:** намеренно внесённая ошибка (например, `<=` вместо `<` в проверке индекса)
роняет тесты.

### A5. Обобщённый список *(растяжка)*

**Цель:** подступиться к тому, как в C делают контейнеры «любого типа».

**Требования:**
- узел хранит `void *data`;
- при создании списка задаются функции сравнения, печати и освобождения элемента;
- продемонстрировать на двух разных типах — `int` и строка (`char *`), причём для строк список
  владеет памятью и освобождает её через переданный деструктор.

## Блок B — новые структуры

Каждая — отдельная директория в `00-c/projects/`, своя пара `.h` / `.c`, свои тесты, свой
makefile.

### B1. Динамический массив — `dynamic-array/`

**Цель:** `realloc`, разница `size` и `capacity`, амортизированная сложность.

**Требования:**
- `push_back`, `pop_back`, `get` / `set` с проверкой границ, `reserve`, `shrink_to_fit`,
  освобождение;
- стратегия роста — удвоение ёмкости.

**Отдельное подзадание:** посчитать и записать в README, сколько раз вызывается `realloc` при
вставке 100 000 элементов при росте ×2 и при росте +1, и объяснить разницу.

**Граничные случаи:** `pop_back` на пустом; `get` с индексом `size`; `reserve` меньше текущей
ёмкости.

### B2. Стек и очередь, две реализации — `stack-queue/`

**Цель:** увидеть, что структура данных и её представление — разные вещи.

**Требования:**
- одинаковый публичный API стека, реализованный дважды: поверх списка из A3 и поверх массива
  из B1;
- то же для очереди; очередь на массиве — кольцевой буфер;
- в README таблица сложностей и вывод, какая реализация когда предпочтительнее и почему.

**Граничные случаи:** извлечение из пустого; для кольцевого буфера — заполнение доверху,
переход индекса через границу, отличие состояния «пусто» от «полно».

### B3. Двусвязный список и сортировка — `doubly-linked-list/`

**Цель:** работа с двумя указателями сразу — типичный источник ошибок.

**Требования:**
- вставка и удаление за O(1) при наличии указателя на узел;
- обход в обе стороны;
- merge sort по списку, без копирования во временный массив.

**Граничные случаи:** удаление головы; удаление хвоста; единственный узел; сортировка пустого
списка и списка из одного элемента; устойчивость сортировки при равных ключах.

### B4. Хеш-таблица со строковыми ключами — `hash-table/`

**Цель:** хеш-функции, коллизии, load factor.

**Требования:**
- разрешение коллизий цепочками (переиспользовать список);
- хеш-функция djb2 или FNV-1a;
- `put`, `get`, `remove`, `size`;
- рехеширование при load factor > 0.75;
- таблица владеет копиями ключей.

**Отдельное подзадание:** посчитать распределение длин цепочек на словаре из ~10 000 слов,
записать в README максимум и среднее.

**Граничные случаи:** `put` существующего ключа — перезапись, а не дубликат; `get` / `remove`
отсутствующего ключа; пустая строка как ключ; рехеширование не теряет элементы.

### B5. Бинарное дерево поиска — `bst/`

**Цель:** рекурсия по структуре и три случая удаления.

**Требования:**
- `insert`, `find`, `remove` (лист / один потомок / два потомка);
- обходы in-order, pre-order, post-order;
- высота дерева;
- полное освобождение;
- обход in-order реализовать **дважды** — рекурсивно и итеративно через собственный стек из B2.

**Граничные случаи:** вставка дубликата (принятое решение задокументировать); удаление корня;
удаление из дерева из одного узла; вырожденное дерево из отсортированной последовательности —
измерить высоту и объяснить, почему она равна n.

## Как проверять

```sh
gcc -std=c17 -Wall -Wextra -Wpedantic -g -O0 *.c -o prog
valgrind --leak-check=full --show-leak-kinds=all ./prog
gcc -std=c17 -g -fsanitize=address,undefined *.c -o prog-asan && ./prog-asan
```

Задание сдано, когда все три команды отрабатывают чисто и тесты проходят.
